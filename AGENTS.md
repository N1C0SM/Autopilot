- Code layout: `src/web` (public site), `src/app` (signed-in app, all platforms), `src/shared` (ui, lib, hooks, integrations, contexts, config, content, types, assets, test); company/agents/design live in `.claude/`. New files go in the matching folder — never recreate `src/components`, `src/pages` or `src/lib` at the root. Build-time files (`seo/`, `src/shared/lib/mcp`) use relative imports, not `@/`.
- Design language (web, iPhone, Android and Mac are one product): read `.claude/design/README.md` before creating or changing any screen and pass `.claude/design/checklist.md` before release — black + restrained gold, borderless 22/28 px cards, pill buttons/fields, big rounded figures, real photos, shared components only.


- Los vídeos de técnica con IA se generan vía la edge function `exercise-video` (AI Gateway, modelo de vídeo por defecto) y se guardan en el bucket público `site-assets` en `exercise-videos/`; el estado del trabajo se guarda en `exercises.video_job_id`.
- Campaign access reads the admin-only settings flag through get_free_campaign; shared resolveFeatures opens only software nutrition/progression, checkout endpoints enforce the pause, and billing records remain unchanged.
- Consumer plan (free/plus/coach) and role (user/trainer/admin) are separate; capabilities resolve only through `supabase/functions/_shared/entitlements.ts` (`resolveFeatures`) — avoids scattered plan checks.
- Stored tier "training" = Plus, "full"/"transform"/"personal" = Coach; Stripe sync mirrors into `entitlements` (source column) so other payment sources can be added later.
- B2B trainer product lives in `product_configs` (key trainer_plan), off by default; flags are enforced server-side in SQL functions/RLS, never only in UI.
- Edge functions call AI only through `supabase/functions/_shared/ai-provider.ts` (aiFetch/getAiConfig), which chains admin OpenAI key -> admin Claude key -> admin DeepSeek key -> Lovable AI (or Lovable only per `app_secrets.AI_PROVIDER`) — one switch for every AI feature. DeepSeek y Claude son SOLO texto: las imágenes y los vídeos de ejercicio exigen OpenAI o créditos de Lovable.
- Every product-like landing section (books, recommendations, future ones) opens a preview modal before any external link: books use BookPreviewModal, everything else ItemPreviewModal with a PreviewVariant — keeps conversion UX consistent.
- Public Free/Plus/Coach cards read `product_configs` (keys free/training/full) via `get_consumer_plans_public`, falling back to `src/shared/config/tiers.ts` — admin edits plans without code changes.
- Username login goes through the `login-identifier` edge function, which signs in server-side and never returns the email behind a username — avoids email enumeration.
- Any copy that mentions Coach or Plus reads `usePlanAvailability()` (`src/shared/lib/planCatalog.ts`), so hiding a plan in Admin → Planes removes it from pricing, FAQs, demo, scan, upsells and the dashboard chat tab at once; shared public copy lives in `src/shared/lib/publicCopy.ts` (pure, also used at build time).
- SEO: `seo/prerender.ts` (Vite plugin) writes `dist/<ruta>/index.html` with per-route head, JSON-LD and real text, plus sitemap.xml, robots.txt, llms.txt and llms-full.txt, using the live plan catalog and blog posts fetched at build time. Republish after changing plans or posts so crawlers see the new state; the files in `public/` are only fallbacks.
- Manual routines carry `custom: true` per day in `training_plan.workouts_json`; generate-plan refuses to overwrite them unless `force: true`, and clients call it via `generatePlanGuarded` (`src/shared/lib/planShield.ts`) — the autopilot never silently replaces user work.
- Admin roadmap persists versions and tasks in admin-only RLS tables; "Hecho" comes only from `src/shared/lib/roadmap/evidence.ts` (reconciled on every load, files checked by tests, mirrored in roadmap-ai/capabilities.ts) or a written admin proof labeled as such — the roadmap can never claim unproven work.
- The uploaded roadmap is a one-time seed catalog with stable task IDs; initialization never overwrites saved edits or resurrects deleted tasks, while the current version is switched atomically through an admin-only RPC.
- Roadmap implementation assistance prepares a copyable Lovable request, never executes code changes from the runtime app, preserving review and release boundaries.
- Test accounts excluded from admin metrics live in the admin-only table metrics_excluded_users (src/shared/lib/testAccounts.ts), toggled from Admin → Usuarios → Acceso; they stay visible in user management.
- Consumer dashboard chat navigation, redirects and rendering share the release gate in `src/shared/lib/releaseScope.ts`, independently of billing entitlements, so unreleased chat never appears as an actionable tab.
- Active workouts use a user-scoped local draft (`src/shared/lib/activeWorkout.ts`) containing the virtual plan, sets and absolute rest deadline; recovery must not depend on the saved training plan or decrementing timers.
- Workout display preferences are user-scoped in `workoutPreferences.ts`; both list and focus views use the same tracker state and persistence to avoid divergent logging behavior.

- App-email feature functions call the shared managed send helper; it preserves admin template overrides and legacy audit rows, while signed email events update retained tables for display only — delivery and send suppression remain platform-owned.
- Authentication verification accepts complete eight-digit OTPs and legacy six-digit OTPs without truncation; auth email accents reuse shared email styles so rendering stays consistent.
- Public social links come only from `settings.social_links` (admin editor, read via `get_social_links_public`, normalized by `src/shared/lib/socialLinks.ts`) for footer and SEO sameAs — never hardcode handles.
